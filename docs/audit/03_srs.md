# Фаза 3 — SRS и нагрузка

Интервалы: Again=0,5 ч; Hard=max(12 ч, 1,5×предыдущий); Good=24/72/168/336/720/1440 ч, затем ×1,5 до потолка 4 320 ч (`scheduler.py:14-29`). Расписание хранит точный UTC timestamp, без округления (`scheduler.py:35-46`).

AUD-03-01 (VERIFIED, S1): слово считается введённым при генерации пака, не при показе (`service.py:203-204`). Сессии берут только первые 12/40 кандидатов (`service.py:281-295`); непоказанные элементы вчерашнего пака больше не входят ни в новый pack, ни в due states. Это создаёт «утерянные» новые слова без state.

AUD-03-02 (LIKELY, S1): capacity недостаточна. Модель реального scheduler и лимитов показывает первый review debt на 4-й день даже при идеальном выполнении; peak debt 29–40, после двухнедельного пропуска 173–196. Вывод: `scripts/srs_summary.csv`. Ограничение модели: sub-day ответы сведены к следующему учебному дню и не импортируется Firestore service.

AUD-03-03 (VERIFIED, S1): Again 30 минут вычисляется, но уже созданная immutable session не регенерируется; ответившая карточка помечается completed по event, а новая сессия этого вида не создаётся. Практически 30-минутный повтор недоступен (`service.py:276-295,322-327`).

Рекомендация: 5–10 новых реально показанных в день; 0 новых при due debt >20; отдельная intra-day learning queue без лимита 12; дневная review capacity минимум 30–40 до стабилизации. При 24/52 фактических ответах и 5–8 сек/карточку чистое свайп-время около 2,6–5,6 мин, без чтения/озвучки.
